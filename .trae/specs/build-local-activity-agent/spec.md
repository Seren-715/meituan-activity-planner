# 本地短时活动规划与执行 Agent Spec

## Why
用户希望只用一句自然语言需求，就能在几分钟内拿到一个可落地的本地短时活动方案，并由系统继续完成预订、下单、分享等关键动作，而不是停留在“搜索推荐”层面。
本次 Demo 需要验证美团式“规划 + 执行”闭环：理解多人出行约束、生成 4-6 小时行程、调用工具检查可用性，并在用户确认后自动完成核心操作。

## What Changes
- 新增一个本地场景短时活动规划与执行 Agent，输入一句自然语言目标，输出完整可执行方案。
- 新增场景理解能力，支持家庭场景与朋友场景，并提取距离、时长、年龄、饮食、人数、出发时间等约束。
- 新增 Planning 策略，按“候选活动生成 -> 约束打分 -> 行程编排 -> 执行动作生成”形成结构化计划。
- 新增 Tool 抽象层与 Mock API，覆盖 POI 检索、餐厅筛选、库存/排队检查、预订、下单、配送、分享。
- 新增确认后执行链路，支持一键完成关键预订/下单动作，并返回执行结果与失败兜底建议。
- 新增 Demo 交互层，命令行或 Web UI 二选一即可，但必须完整展示输入、规划、确认、执行、分享闭环。
- 新增设计文档内容，说明 Planning 策略、工具调用链路、异常处理机制。
- 新增比赛版分阶段推进要求，后续演进需适配“非每日连续开发、白天需上课”的实际节奏。
- 新增里程碑式交付要求，把后续工作拆成可独立完成、可随时中断恢复的阶段任务。

## Impact
- Affected specs: 活动需求理解、短时行程规划、工具编排执行、结果分享、异常恢复
- Affected code: Demo 入口层、Agent 编排层、Planner、Executor、Tool 接口、Mock API、设计文档、比赛版后续排期与交付节奏

## 设计说明
### Planning 策略
- 第一阶段：意图解析。识别出行对象、人数结构、时间窗口、距离约束、隐含偏好与预算信号。
- 第二阶段：候选生成。分别生成“主活动”“餐饮”“补充活动”候选集合，并过滤不适配人群的选项。
- 第三阶段：方案评分。以路程合理、群体匹配、时长可控、衔接顺畅、执行成功率高为主要维度打分。
- 第四阶段：执行编排。把最终方案转成动作序列，包括查询、预占位、预订、下单、配送、分享。

### Tool 调用链路
- `ParseGoalTool`：抽取结构化约束。
- `SearchActivityTool` / `SearchRestaurantTool`：获取活动与餐饮候选。
- `CheckAvailabilityTool`：查询是否营业、是否有号、是否可预约。
- `BuildItineraryTool`：组合成 4-6 小时完整方案。
- `ReserveTool` / `OrderTool` / `DeliveryTool`：执行预约、下单、配送等动作。
- `SharePlanTool`：生成发送给家人或朋友的确认文案。

### 异常处理机制
- 工具超时：返回降级候选，保留已验证成功的方案部分。
- 资源不可用：自动回退到同商圈或相似标签备选项，并重新计算时长。
- 部分执行失败：展示成功/失败动作清单，不回滚已成功动作，提供人工确认后的补偿动作。
- 用户约束冲突：提示冲突项并给出 1-2 个最小改动建议。

### 分阶段推进原则
- 后续比赛版开发按“可独立交付、可中断恢复、每阶段可演示”进行拆分，不依赖连续多天大块时间。
- 每个阶段都应在 1-3 次短时开发内形成可见成果，避免必须连续多天编码才有结果。
- 优先顺序固定为：真实本地能力 -> Web UI 展示 -> 可用性与执行增强 -> 体验打磨与答辩材料。
- 每个阶段结束时都要保留可运行版本，避免因课程安排导致中断后难以恢复。

## ADDED Requirements
### Requirement: 自然语言目标理解
系统 SHALL 从一句自然语言目标中提取活动规划所需的结构化约束，包括场景类型、人数、时间窗口、距离偏好、特殊人群需求和待分享对象。

#### Scenario: 识别家庭场景约束
- **WHEN** 用户输入“今天下午空着，想和老婆孩子出去玩几个小时，别离家太远”
- **THEN** 系统识别为家庭场景
- **AND** 提取孩子年龄、成人饮食/减脂需求、时长与距离约束

#### Scenario: 识别朋友场景约束
- **WHEN** 用户输入“4 个人下午想出去玩和吃饭，别太折腾”
- **THEN** 系统识别为朋友场景
- **AND** 提取人数结构、社交型活动倾向与时长约束

### Requirement: 生成完整 4-6 小时方案
系统 SHALL 生成覆盖“去哪玩 -> 去哪吃 -> 是否追加活动”的完整可执行方案，并明确每段预计开始时间、持续时长、路程与选择理由。

#### Scenario: 输出组合式行程
- **WHEN** 结构化约束已经生成
- **THEN** 系统输出至少 1 条主推荐方案
- **AND** 方案包含活动、餐厅、补充活动或返程建议
- **AND** 总时长控制在 4-6 小时内

### Requirement: 餐饮与活动可用性检查
系统 SHALL 在生成最终推荐前检查关键资源是否可用，包括餐厅是否营业、是否适合目标群体、是否有位置或需要排队，以及活动是否可预约。

#### Scenario: 餐厅需要排队
- **WHEN** 推荐餐厅当前无即时座位
- **THEN** 系统展示预计等待时间或预约要求
- **AND** 提供至少 1 个可替代餐厅

#### Scenario: 活动不可预约
- **WHEN** 首选活动预约失败或库存不足
- **THEN** 系统切换到同类备选活动
- **AND** 重新输出调整后的完整行程

### Requirement: 确认后自动执行关键动作
系统 SHALL 在用户确认方案后，自动完成关键预订或下单动作，并返回逐项执行结果。

#### Scenario: 一键执行
- **WHEN** 用户确认最终方案
- **THEN** 系统依次完成预约、排号、下单或配送等关键动作
- **AND** 返回每个动作的状态、凭证或失败原因

### Requirement: 生成可分享的计划摘要
系统 SHALL 在规划完成或执行完成后，生成一段可直接发送给家人或朋友的自然语言摘要。

#### Scenario: 分享给家人或朋友
- **WHEN** 行程已经确定
- **THEN** 系统输出类似“下午 2 点出发，先去……随后去……预计……结束”的摘要文本
- **AND** 文本包含集合时间、主要地点、餐饮安排与注意事项

### Requirement: Demo 与 Mock Tool 可独立演示
系统 SHALL 以本地 Demo 形式交付，并包含完整 Tool 实现代码与 Mock API，保证在无真实外部依赖情况下可完整演示规划和执行链路。

#### Scenario: 本地演示闭环
- **WHEN** 评审者启动 Demo 并输入自然语言目标
- **THEN** 可以看到规划、确认、执行、分享的完整链路
- **AND** 所有外部资源调用均由 Mock API 响应

### Requirement: 比赛版开发节奏可中断推进
项目后续演进 SHALL 采用适配低频开发节奏的阶段式推进方式，保证开发者即使不能每天投入，也能稳定迭代比赛版本。

#### Scenario: 开发者白天上课且无法每日开发
- **WHEN** 开发者只能在部分晚上或周末投入时间
- **THEN** 后续任务仍可按独立阶段推进
- **AND** 每个阶段都有清晰输入、输出与验收标准
- **AND** 中断后可以从最近阶段继续，而不需要大范围返工

#### Scenario: 比赛前逐步提升完成度
- **WHEN** 距离比赛截止还有二十多天
- **THEN** 项目按里程碑逐步从本地 Mock Demo 演进到更完整的比赛版
- **AND** 优先完成真实本地检索、Web 展示、执行可信度和演示稳定性
